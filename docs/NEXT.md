## 3. 工作方式（每批）

1. **在 worktree 開分支**：`git worktree add ../_wt/<分支> -b feat/<第一個 task 編號>-<slug>`。
2. **只讀需要的段落**：`CLAUDE.md`、這份、`ROADMAP.md` 的該批、該批 task 所在的 epic 段落、相關的 `ARCHITECTURE.md` 章節。不要整本讀；歷史檔只用搜尋。
3. **做完跑** `npm run lint && npm run typecheck && npm test && npm run build`，只看最後 5 行。動到前端的批次再跑 `npm run budget -- --chunks`，把每條首屏線的 bytes 寫進 PR（D4 的規則）。介面字串改了跑 `npm run check-i18n`。
4. **一批一個 ready PR**：標題英文、結尾列出全部 task 編號；本文（繁中）寫對應 AC、怎麼驗證、實測結果（卡丁車多人要兩台裝置）。
5. **在同一個 PR 更新文件**：epic 勾選 task（寫 PR 號）、AC 勾選（有驗證才勾）、`PRD/README.md` 進度表、`ROADMAP.md` 該批 `[x]` 與 PR 號（路線圖外的在表尾加一列）、這份 §1 加一兩行、§5 刪掉做掉的、新的已知限制加進 §5。
6. **CI 綠了直接合併**（`gh pr merge --squash --delete-branch`），需要人決定的事才停下來問（加進 §2.1）。
7. 合併後回報：做了什麼、PR 號、下一批是哪一批、有沒有等人決定的事。

**容易踩的地方**：

- **陞官圖完整版的規則版本**：state 有 `rulesVersion`；改規則或圖版不要改舊的一套（指紋測試擋），要改就開新一套；格子只能新增（id 存在進行中的局裡），加格子同時放進 `departments.ts`；改完跑 `npm run sim:promotion`。簡化版的 `score` 是官階、完整版是銀兩。
- `RoomView` 只能由已存狀態推導，改變一律走 `change()`。
- 卡丁車：改物理或車款要重跑 `npm run kart:feel`、`kart:meta`（podium 貼回 `shared/kart/meta.ts`）、`kart:medals`（寫進 `src/kart/challenge/medalTable.ts`）；改賽道要加 `revision`。新賽道的專屬場景登記在 `src/kart/art/trackScenery.ts`、新車加進 `src/kart/art/bodyLoad.ts` 的 `BODY_FAMILY`、新歌放 `src/kart/audio/songBook/`（測試擋）。
- 新遊戲上大廳前先看首屏預算；遊戲字串照默契牌局的做法，只把大廳與等待室要的放首屏。

## 4. 不要做的事

- 不要重做規劃、不要改批次順序；覺得順序有問題就在回報裡說，讓擁有者改 ROADMAP。
- 不要在 JSX 寫裸字串；介面文字一律 `t('key')`，en 與 zh-TW 同時加。
- 不要加入任何原作（跑跑卡丁車、紙牌幫、腦洞量表、ito、瞎掰王、衰事無極限／Shit Happens）的名稱當作自己的名稱、美術、題目文字、音樂、模型；賽道不可重製原作地圖；不確定就看 `docs/PRD/01-legal-ip-analysis.md` §4。
- 不要把模型、貼圖、音檔 commit 進 repo（走 R2 與 `docs/ASSETS.md`）；小於 100 kB 的 SVG／PNG 圖示可以。
- 不要直接推 `main`、不要 force-push。
- 不要再把逐 PR 的長段落寫進這份或 ROADMAP（放 PR 本文與設計文件）。
