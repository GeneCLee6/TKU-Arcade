## 1. 模型一句話

**每台車由自己的瀏覽器模擬（`shared/kart/physics.ts`，60 Hz），每 3 步送一次自己的狀態（20 Hz）；RoomDO 不跑物理，只把每個 frame 轉給其他人，順便用賽道的檢查點裁定圈數、完賽與名次。** 朋友圈用，合理性檢查是擋 bug，不是反作弊。

## 2. 線上的東西

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 瀏覽器 → 房間 | 二進位 32 bytes（`shared/kart/net.ts`） | kind、旗標（重置、甩尾、噴射、側滑、自己算完賽、甩尾方向）、車與角色（低 4 bit 車、高 4 bit 角色，N3）、方向盤、**賽道 tick**（GO 起算的 1/60 秒步數，GO 前是負的）、x、z、朝向、vx、vz、穿過起終點線次數、下一個 gate、序號 |
| 房間 → 其他人 | 二進位 33 bytes | 前面加一個 byte 的座位，後面原封不動 |
| 瀏覽器 ↔ 房間 | 二進位 9 bytes → 17 bytes（`CLOCK_FRAME` 255 開頭，`shared/protocol.ts`） | 對時：float64 的瀏覽器 `performance.now()`，回來時後面多一個 float64 的伺服器 `Date.now()`。用二進位是因為 JSON 的解析程式會進每個人的首屏 |
| 其他（裝好了、倒數、每一圈、完賽、退賽、結果） | 照舊的 JSON patch（協定 v2 起陣列也只送差異，§15） | `kart` 這款 GameModule 的 state，存在 DO，走 `reduce`，可以重播 |

二進位 frame 不進 storage、不改 `rev`、不走 `change()`：每秒 20 次 × 8 人寫 storage 太貴。二進位 frame 沒有讓協定升版（回合制的房間收到二進位照舊關閉連線；對時的 frame 任何房間都回）；2026-11-17 patch 的陣列差異升到 v2（§15）。

## 3. 時間

- **對時**：進賽道先連問 5 次（間隔 250 ms），之後每 2 秒一次；取**最近 10 次裡來回最快的那次**，假設伺服器在來回的正中間讀錶（NTP 的想法）。`offset = s − (送出 + 收到) / 2`。
- **起跑**：大家都畫好賽道（或等了 25 秒）→ 倒數；房間在同一個瞬間用自己的錶定 `goAt = now + 4000 ms`（`realtime.clock`），同時開 `go` 計時器。每個瀏覽器用對好的錶自己數到 `goAt`：前 1 秒「準備」，最後 3 秒 3、2、1。單機的**起跑加速**照用（最後 0.35 秒按油門並按住），因為倒數本身就是時間賽的倒數，只是秒數換成房間的。
- **賽道時間**用每台車自己的 tick（GO 起算的步數）：網路抖動不影響成績。伺服器只擋「比伺服器的錶快 1 秒以上」的 tick。

## 4. 伺服器裁定（`shared/kart/race.ts` 的 `judgeFrame`）

| 檢查 | 門檻 | 不過 |
| --- | --- | --- |
| 速度 | **那台車的**最高速 × 疊噴倍率 × 1.5（N3 起每台車不同：標準 60 × 1.6 × 1.5 = 144 m/s，最快的白鷺 146.9、最慢的 142.6；車由 frame 的車 byte 決定，不認得就用最快的） | 丟掉，不轉送 |
| tick 比伺服器快 | 1 秒 | 丟掉 |
| 跳太遠（不是重置） | 上面那台車的速度上限 × 間隔 + 12 m | 丟掉 |
| 重置落點 | 離某個復位點或自己的起跑格 30 m 內 | 丟掉 |
| 比上一個還舊 | — | 丟掉 |
| 連續被丟 1 秒 | — | 下一個直接當作現在位置（不算路上的 gate），免得卡死 |

- **檢查點**：伺服器用上一個 frame 到這一個的線段，照 `course.ts` 的 `passGates` 一個一個算（一個 frame 最多 3 個 gate），倒著穿過會退回。**車自己的計數**只在「剛好比伺服器多一個 gate、而且人就在那個 gate 後面 60 m 內」才採信（掉一個 frame 可能把穿越藏起來），或伺服器忘了（DO 被趕出記憶體）而車說的圈數和已記錄的一樣時拿來接回。
- **一圈**：起終點線往前穿過、完成圈數多一，就送 `lap { seat, ms }`（`ms` 用穿越點在兩個 frame 之間的比例內插 tick）；最後一圈就是完賽時間。
- **結束**：所有人完賽或退賽；或第一個完賽後 30 秒；或每圈 4 分鐘的上限。還在跑的算「未完賽」，依完成圈數排。
- **斷線**：比賽中 20 秒沒收到某台車的 frame（在別人的 frame 進來時檢查）就 `retire`。

## 5. 其他車怎麼畫（`src/kart/race/remotes.ts`）

- **插值**：每台車畫在它最新 frame 之前 **100 ms**，取前後兩個 frame 線性內插（朝向走短的那邊）。
- **每台車自己的時鐘差**：「到達時間 − frame 的 tick 時間」取 3 秒內最小的，所以分頁變慢或對時有點偏，不會讓車一直在外推。
- **外推**：超過最新 frame 時沿速度往前最多 **200 ms**，再久就停住並標記為 stale。
- **重置**：清掉舊的 frame，直接跳過去，不畫中間。
- **名牌**：每幀把車頂 2.4 m 的點投影到畫面，用 DOM 移動（不經過 React）。
- **連線不穩**：對時來回超過 300 ms、5 秒沒有回應、或有車 stale，持續 1.5 秒才顯示「連線不穩」。

## 6. 車對車碰撞（`bumpKart`）

各自在本機算：自己的車和**畫面上的**其他車（不含 stale）重疊就各推開一半，朝對方的相對速度 × (1 + 0.3) / 2 反彈，最少推 2 m/s。結果不送出、不同步，兩邊螢幕可能差一點，朋友之間可以接受。

### 8.1 機器人壓測（`e9-t11` 的數據部分，2026-11-17）

`npm run kart:loadtest -- --url <站> [--bots 6] [--track oldstreet] [--laps 3] [--mode items] [--json out.json]`（`scripts/kart-loadtest.ts`）。一個 Node 程序裡開 N 個機器人（暱稱 `bot-1`…`bot-N`，第一個是房主），**用真的協定**：`POST /api/rooms` 開私人房 → 每個機器人開 WebSocket `join` → 自動入座 → `set_look` 選車（六台車、四個角色輪流）→ 房主 `start` → `loaded` → 對時（同 `netRace.ts`：先 5 次、之後每 2 秒）→ 數到房間的 `goAt` → 用 `shared/kart` 的物理（各自的車款參數）＋`?autopilot` 的駕駛（`src/kart/race/autopilot.ts`）每 3 步送一個 frame → 拿箱、用道具、套用別人的道具效果（同 `netRace.ts` 的 `adjust`，含調包的跳躍與重置 frame）→ 完賽 → 房主 `dissolve`（關閉碼 4412，不留殘房）。機器人只在沒拿道具時會稍微轉向前方 30 m 內的箱子（自動駕駛只走路中間，燈籠老街的箱子大多不在中線上）；停住 4 秒會自己重置。**不撞別的車**（`bumpKart` 沒接）、不畫畫面。**預設對本機；正式站要擁有者明說並加 `--allow-production`**。

**怎麼量**（純邏輯在 `scripts/kart/loadtest-report.ts`，測試 `tests/scripts/kart-loadtest.test.ts`）：

- **頻寬**：每個 WebSocket 訊息的 payload，加上 WebSocket 標頭（瀏覽器送的多 4 bytes 遮罩）算「線上」；TCP／TLS／IP 不算。只算 GO 到比賽結束那段。
- **轉送延遲**：機器人都在同一個程序，用同一個錶：「A 送出 → B 收到」，沒有對時誤差。另外也照瀏覽器的做法用對好的錶算「收到的伺服器時間 − frame 的 tick 時間」，這個數字還包含送的那台車起跑時對齊 GO 的誤差（約 ±1 步，所以可能是負的），只當參考。
- **丟 frame**：比賽中送出的 frame，其他機器人**一個都沒收到**的就是被房間丟掉（伺服器不回原因）；原因用機器人自己跑一次同樣的 `judgeFrame`（用對時估的到達時間）推測。比賽結束前 1 秒內送的不算（房間收到時可能已經不裁定）。
- **圈數裁定**：伺服器的 `lapMs`（running total）和機器人自己的 `Trial.laps` 比，差 60 ms 內算一致（伺服器在兩個 frame 間內插，機器人算整步）。
- **時鐘**：所有機器人用同一個錶，所以各自估的 offset 互相差多少，就是對時的誤差。

道具（同一順序）：本機 6 人拿箱 46 次、用了 45 個（順風 9、泡泡罩 10、冰雹 8、泥水坑 9、拖繩 4、雷雲 2、調包 2、逆風 1），投射物打中 13 次（泥水坑 9、冰雹 2、雷雲 2），泡泡罩擋下 2 次；本機 8 人拿 60 次，打中 13 次；`wrangler dev` 6 人打中 7 次、8 人打中 16 次（雷雲 8）。每場都有調包（伺服器收下跳躍的重置 frame，沒有被當成「跳太遠」丟掉）。

**看到的**：

1. **流量和估的一樣**：每人上行 640 B/s 的 frame（20 × 32），加上標頭與對時約 0.77 kB/s；8 人房每人下行的 frame 4.6 kB/s 正好是 7 × 20 × 33。
2. **道具賽的 JSON patch 不小**：每人約 1.5（6 人）–2.0（8 人）kB/s，佔下行三成。原因是 patch 對陣列整個替換（`shared/patch.ts`）：每次拿箱、用道具、命中，`racers`（每人一筆）、`boxes`（30 個數字）、`events`（最多 16 筆，含調包的落點）、`shots` 整個重送。現在的量（< 7 kB/s）對家用網路與手機都不是問題，先不改；要省可以讓 `events`／`shots` 只送新增的（記在 `NEXT.md`）。**已處理**（§15）：patch 對陣列也只送差異，6 人道具賽的 JSON 從每人約 1.5 降到約 0.36 kB/s。
3. **伺服器裁定沒有誤殺**：6 場 112,000 多個 frame，一個都沒被丟，也沒有轉送後遺失的；調包、重置、完賽後的 frame 都照收。圈數和機器人自己算的最多差 20 ms（一個 frame 50 ms 以內）。
4. **轉送延遲**：本機的 DO 轉送本身是個位數毫秒；p99 的 20–35 ms 與偶爾 300 ms 以上的最大值，是同一台筆電上 8 個機器人（每個都跑 60 Hz 物理）加 dev server 搶 CPU，不是協定。真的網路見下面預覽站那列。
5. **預覽站（真的網路）**：「A 送出 → 房間 → B 收到」p50 約 40 ms、p95 58–70 ms、p99 82–90 ms，大約就是一個對時來回（38–41 ms，同一條家用網路上去再下來）；8 人和 6 人差不多，房間的轉送沒有因為人多變慢。加上 §5 的 100 ms 插值緩衝，別人的車大約畫在 140 ms 前的位置。
6. **對時**：同一個錶的機器人估出的 offset 彼此差 0.5–2.8 ms（本機與預覽 6 人）、預覽 8 人 10.9 ms（有一個機器人最快的那次來回比較慢），倒數同步都在一個 frame 內。

**限制**：機器人不會撞車、不甩尾（自動駕駛很保守，一圈約 41–44 秒），所以「別人的車看起來順不順」「被打中時手感」量不到；所有機器人在同一台電腦、同一條網路，量不到不同裝置與手機網路的差異（`e9-t04`）；伺服器端的 CPU 時間看不到（本機沒有，預覽站要看 Cloudflare 儀表板）。

## 9. 自己一個人測

房間網址後面加 **`?autopilot`**（例如 `/r/<id>?autopilot`）：那個分頁的車會自己沿路中間開（不甩尾、很保守），可以開兩個瀏覽器（或一般＋無痕視窗，同一個瀏覽器的兩個分頁會被當成同一個人）自己跟自己比。最少 1 人就能開賽。

要一次很多台車（不開瀏覽器）：`npm run kart:loadtest -- --url http://localhost:5175 --bots 8`（§8.1）。先 `npm run dev`；或 `npm run build` 後 `npx wrangler dev -c dist/tku_arcade/wrangler.json`。印出 Markdown 表格，`--json` 另存完整數字；全部完賽、圈數一致、房間有解散才回 0。想在房間裡看機器人跑，可以在它們入座後自己用瀏覽器進同一個房間（比賽中進來就是觀戰）。

## 10. 道具賽（L4，2026-11-16）

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 瀏覽器 → 房間 | 二進位 8 bytes（`shared/kart/items.ts`） | kind 2、op（1 拿取、2 使用）、箱子編號或道具編號、0、int32 賽道 tick。**不轉送** |
| 房間 → 大家 | JSON patch | `got`／`use` 兩個 `system` 動作改的 state：`boxes`、每人的 `item`／`shieldUntil`、最近 16 個 `events` |

- **拿取**：瀏覽器自己的車離箱子中心 2.6 m 內、手上沒東西、箱子在（`boxes[i]` ≤ 伺服器時間）就送；送出後 0.7 秒內不再送，那個箱子在本機先藏起來。伺服器要求：道具賽、比賽中、手上沒東西、箱子在、最後看到的位置到「往前 0.25 秒」的線段離箱子 12 m 內。同一個箱子兩個人搶，先到房間的拿到；箱子 3 秒後回來。
- **抽**：名次用伺服器記憶體裡每台車的 gate 進度（完賽的排最前），第一名「前段」、最後一名「後段」、其他「中段」；`rollFor(seed, draws)` 決定性。
- **使用與命中**：伺服器用最後已知位置決定對象：拖繩＝正前方那台（160 m 內）；逆風＝前面所有人；調包＝正前方那台（同一圈、260 m 內）。泡泡罩（逆風、調包會被擋）在 `use` 那一刻判斷。沒有對象就不回動作，道具留在手上，瀏覽器 0.9 秒後提示「前面沒有人在範圍內」。
- **效果**：每個瀏覽器讀 `events` 新的那幾個，用 `at`（伺服器時間）加上持續時間算還剩多久，自己套到自己的車上；別人的車照舊從 frame 畫（被逆風吹的車看起來就是變慢了）。調包的兩台車各自跳到 `warps` 給的位置、帶重置旗標送一個 frame，伺服器照收。
- **延遲**：拿取與使用都要等房間回 patch（約一個來回，家用網路 60–120 ms）才看到道具、才生效（被投射物打中的那一方 2026-11-17 起本機預測，§15）。朋友之間可以接受；之後覺得鈍可以讓順風、泡泡罩在本機先生效。

### 10.1 投射型道具（L5 `e9-t06b`，2026-11-17）

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 瀏覽器 → 房間 | 同 §10 的 8 bytes `use` | 道具編號 5–7（`hail` `cloud` `puddle`），格式不變 |
| 房間 → 大家 | JSON patch | `use` 多帶一個 `shot`，放進 state 的 `shots`（最多 24 個）；命中是新的 `system` 動作 `hit`（`seat`、`shot` 編號、`at`），從 `shots` 拿掉並加一個 `events`（`hit: true`） |

- **一顆投射物＝起點、時間、速度、結束時間**（`shared/kart/shots.ts` 的 `KartShot`）。任何時刻在哪都由這幾個數字算出來，所以 state 不用逐格推進，重播也一樣。
- **冰雹**：從伺服器最後看到的位置、朝車頭方向，速度 84 m/s 加上丟的人往前的速度；射程 220 m，丟出那一刻沿射線找第一道牆（含路緣），撞到就停（`rayToWall`）。丟的人自己不會被打到。
- **雷雲**：對象是正前方那台（320 m 內，沒有就拒絕、道具留在手上，同拖繩）；飛行時間＝距離 ÷ 95 m/s，夾在 0.7–3.5 秒。時間到時那台車的下一個 frame 就算命中（不看位置，只能用泡泡罩擋）；1.5 秒內沒有 frame 就算了。
- **泥水坑**：放在車後 3.6 m，留 20 秒；誰開進去都算（自己 0.9 秒後也算）。
- **命中裁定**：每台車的 frame 進來時（`realtime.frame`，在 `judgeFrame` 收下之後），拿這台車「上一個 frame → 這個 frame」的直線，和每顆投射物在同一段時間的直線比最近距離（`closestApproach`，兩條都是等速直線，有解析解），小於車半徑＋投射物半徑就打到；只算兩者都存在的那段時間。重置、調包的跳躍、或兩個 frame 隔超過 1 秒時，只看這個 frame 的位置。一個 frame 最多一次命中。完賽的車不會被打到。
- **泡泡罩**：在 `hit` 那一刻判斷（`shieldUntil > at`），擋下就連投射物一起消失，`blocked` 記著那台車。
- **效果**：被打到的瀏覽器從 `events` 讀到 `hit`，`at` 起暈 1.1 秒（冰雹）／1.5 秒（雷雲）／1.0 秒（泥水坑）：噴射全滅、速度用每秒 5 倍的比例壓到極速的 25%（`stunStep`）。別人的車照舊從 frame 畫。
- **畫面**：每個瀏覽器用同一組數字畫投射物（`netRace.ts` 的 `props`）；雷雲朝目標「在這個瀏覽器看到的位置」飛，到時間剛好到，命中與否仍以伺服器為準。命中要等伺服器收到被打那台車的 frame 再回 patch，所以被打的人大約晚一個來回才暈（60–120 ms），丟的人看到冰雹穿過對方之後一點點才出現「打中」。**2026-11-17 起**（§15）：被打的那台自己的瀏覽器先預測（馬上暈、轉），其他人從收到 patch 起算、別人的車再晚 100 ms 才轉。
- **被打中的樣子**（2026-11-17）：被打的車打轉、彈跳、噴星光，泡泡擋下會破；每個瀏覽器（車手、觀戰、重播）都從同一個 `hit` 事件推導，不用新的線上格式（`ARCHITECTURE.md` §4.19）。即時的起點從收到時算（§15），重播用事件的 `at`。

## 11. 觀戰與重播（L5 `e9-t10`，2026-11-17）

### 觀戰

- **不用新的線上格式**：房間本來就把每個 frame 轉給**所有已 join 的連線**（§2），旁觀者也收得到。觀戰畫面（`src/kart/watch/SpectateView.tsx`）用跟車手畫別人一樣的 `remotes.ts`（100 ms 緩衝、外推 200 ms），只是沒有自己的車，攝影機跟著選的那台。
- **誰會看到**：比賽中才進房間的人（沒有座位）、沒入座的人、被判退賽的人預設就是觀戰；完賽的車手在完賽面板按「看其他人跑」。可以關掉回到名次表（再按「即時觀戰」回來）。
- **操作**：下一台／上一台（← →、A D、Q E；手把 LB RB 或十字鍵左右）、換視角（V、C；手把 Y）：車後或**俯瞰**（車上方 55 m、後方 18 m）；右上角小地圖標出被跟的車。HUD 顯示被跟的人的名字、名次（伺服器的完賽順序＋各車最新 frame 的進度，`shared/kart/watch.ts` 的 `watchOrder`）、第幾圈、道具。道具箱與泡泡罩用房間的 view 畫，時間用旁觀者自己的對時（`serverClock.ts`，跟車手一樣的 ping，間隔 3 秒）。
- **流量**：旁觀者跟車手收一樣多（8 人房 140–160 個 frame／秒，約 5 kB/s）；房間每多一個旁觀者，每個 frame 多送一份。朋友圈的房間可以接受。

### 重播：資料從哪來

**每個瀏覽器自己錄它收到的廣播**（`src/games/kart/useRaceRecorder.ts`，掛在比賽畫面底下，從起跑格到結果一直錄，不管畫面在比賽、觀戰還是名次表）：別人的 frame 從轉送來的、自己的在送出時順便錄。房間不多存、不多送任何東西。

| 做法 | 房間（DO）記憶體 | 額外流量 | 缺點 |
| --- | --- | --- | --- |
| **瀏覽器自己錄（採用）** | 0 | 0 | 中途才進來的人只有進來之後的；自己掉的 frame 在重播裡是內插的直線；每個人的重播差一點點（自己的車比較細） |
| 房間在記憶體錄、賽後送給大家 | 8 車 × 3 分鐘約 216 kB（DO 上限 128 MB，不是問題） | 賽後每人一次約 216 kB（8 人房共 1.7 MB） | 比賽結束後沒人送 frame，DO 可能在幾秒內進休眠、記憶體清空，重播就沒了；要不就是寫 storage（一場一次 ≤ 216 kB 可以，但 `RealtimeModule` 要多一個「賽後」的掛鉤，`room-host` 要多一種下行訊息） |

選前者：不用改協定與 RoomDO、不怕 DO 休眠，代價只有「晚來的人重播不完整」（畫面會寫「從你進房間時開始錄」）。之後要存 R2 或讓晚來的人也有整場，再走第二種，格式已經準備好（下面的 `encodeReplay`）。

### 重播：格式與大小（`shared/kart/replay.ts`）

- **降頻**：每台車最多每 6 個 tick（0.1 秒）留一個樣本；重置（跳躍）、完賽旗標變了一定留。起跑前只留最後 1 秒（tick ≥ −60），用來畫起跑格。
- **差分**：第一個樣本、重置、或離上一個超過 327 m／255 tick 時存絕對位置（14 bytes：旗標、int32 tick、兩個 float32、車身）；其他存差分（6 bytes：旗標、uint8 tick 差、兩個 int16 公分差）；後面都接 9 bytes（int16 朝向 ×10000、int16 vx vz ×100、int8 方向盤、圈數、下一個 gate）。差分以**解出來的位置**為基準，誤差不會累積（測試：2 分鐘的路線每個樣本都在 1 公分內）。
- **大小**：一個樣本 15 bytes、每秒 10 個 ＝ **每台車 150 B/s**（線上是 32 bytes × 20 ＝ 640 B/s，約 1/4）。8 台 × 3 分鐘 ≈ **216 kB**；常見的 4 人 2 圈（約 1.5 分鐘）≈ 54 kB。都在瀏覽器記憶體，下一場（新的 seed）就換新的。
- **其他**：用掉的道具（`events` 的伺服器時間減 `goAt` 換成 tick，從瀏覽器開始聽之後的才算）、每人手上的道具何時變（房間沒說何時拿到，用「目前收到最新的 tick」，差一個來回）、每圈時間與完賽時間（比賽結束時的 view）。
- **一包**：`encodeReplay`／`decodeReplay` 把上面打成一個 `Uint8Array`（magic、版本、JSON 的其他資料、每台車的樣本），現在只有測試用，留給之後存 R2 或下載。

### 重播：播放（`src/kart/watch/ReplayView.tsx`）

- 結果面板多一個「看重播」（這個瀏覽器有錄到東西才有）。時間軸從 GO（晚來的人從第一個樣本）到最後一人完賽後 2 秒；有人沒完賽就到最後一個樣本。
- 每幀用 `sampleAt` 在前後兩個樣本間內插（朝向走短的那邊，遇到重置不內插、直接跳）；名次用同一個 `watchOrder`，完賽的人在他完賽的那一刻之後才排到前面。
- 播放／暫停（空白鍵、K、手把 A）、±5 秒（J L、手把扳機）、0.5×／1×／2×／4×（− +、手把十字鍵上下）、拖時間軸、換車、換視角都和觀戰一樣。泡泡罩照 `events` 重畫（用掉起 8 秒、擋下一次就破）；投射物（§10.1）照錄到的 `shots` 重畫（起點、時間、速度算位置；提早從 `shots` 消失的在那一刻收掉，誤差約一個來回）；道具箱不畫（不知道每個箱子何時被拿）。
- **測試**：`tests/kart/replay.test.ts`（降頻與差分的大小、1 公分內、重置與遠跳存絕對、截斷不越界、內插與朝向、重置不內插、圈數／道具／泡泡罩在某一刻、錄製與道具 tick、一包來回、8 台 3 分鐘的大小、時間軸起訖、播放／倍速／拖曳／播完重播）、`tests/kart/watch.test.ts`（名次、換車、按鍵與手把）、`tests/kart/raceRecorder.test.tsx`（自己的 frame 送出時錄、別人的收到時錄、新的一場重來）、`e2e/kart-race.spec.ts`（比賽中第三個人進來看到觀戰並換車；結束後開重播，時間軸會走、可以暫停）。

## 12. 車款與角色（N3，2026-11-17）

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 瀏覽器 → 房間 | JSON `{ t: 'set_look', look }` | 等待室裡（任何狀態都收）：`look` 是 `kart.driver`（例 `heron.club`），null 拿掉。房間只檢查格式，存在成員上，所有人的 `RoomMember.look` 都看得到 |
| 比賽中 | frame 第 2 個 byte | 車 index（低 4 bit）＋角色 index（高 4 bit）（`shared/kart/karts.ts`）。別人的畫面照這個畫車與角色；伺服器照這個決定速度上限 |

- **車是瀏覽器自己說的**：選最快的車只會讓上限高 2%（白鷺），合理性檢查仍是擋 bug，不是反作弊（§1）。
- **車撞車**照兩邊的重量分推力（輕的被推得多），仍是各自在本機算（§6）。
- **觀戰與重播**（§11）也照這個 byte 畫車與角色：重播的樣本本來就把整個 byte 存下來（絕對樣本的 `u8 body`），不用改格式。

## 13. 待擁有者：真人手感實測（`e9-t11` 的另一半）

數據的部分（流量、延遲、裁定負載、圈數與道具裁定）機器人量完了（§8.1）。剩下只有人能判斷的，找 5 位朋友、各用自己的裝置（至少一位用手機熱點）開一間**道具賽**跑完 3 圈，記下：

1. 別人的車順不順（會不會抖、瞬移、卡住）；有沒有出現「連線不穩」，多常。
2. 拿箱、用道具的反應慢不慢（要等一個來回，§10）；被打中是不是馬上轉（本機預測，§15），有沒有「沒被打到卻暈了」；被雷雲或冰雹打到時覺得公不公平。
3. 撞別人的車（各自在本機算，§6）兩邊看起來差多少，能不能接受。
4. 6 人起跑擠在一起、道具一多時，畫面與幀數撐不撐得住（尤其手機）。
5. 有人中途斷線再回來，或有人在比賽中進來觀戰，房間有沒有怪事。

有問題丟給 AI 協作者；說「多人 OK」就勾 `e9-t11`；`e9-t04`、AC-9.6 還要兩種網路的數字（§8 的「還沒做」）。

## 14. 多人房的電腦車（2026-11-17，`feat/kart-room-bots`）

房主在等待室加的電腦車由**房主的瀏覽器**模擬（`src/kart/bots/roomBots.ts` 跑 `botRace.ts`），以電腦車的座位送 frame；房間照常裁定。架構與理由在 [`ARCHITECTURE.md`](ARCHITECTURE.md) §4.21。

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 房主 → 房間 | JSON `{ t: 'add_bot', level, look? }` | 等待中或結束後；放最低的空座位，名字由房間取。移除用 `kick`（電腦車不記 ban，比賽中拒絕） |
| 房間 → 大家 | `RoomMember.bot = { level, name }` | `name` 是名字的 id，瀏覽器用 `games.kart.bot.name.<id>` 顯示；`online`、`ready` 永遠是 true |
| 房主 → 房間 | JSON `{ t: 'action', action, botSeat }` | 替電腦車的座位送 action（只有 `loaded` 會用到） |
| 房主 → 房間 | 二進位 `254`、座位、原本的 frame（34 bytes；道具 frame 是 10 bytes） | `shared/protocol.ts` 的 `PROXY_FRAME`／`proxyFrame`。裡面的 frame 和那個座位自己的瀏覽器送的一模一樣 |
| 房間 → **所有人（含房主）** | 二進位 33 bytes | 照 §2：電腦車的座位在前。房主也收得到，所以房主的畫面從 frame 畫電腦車，和畫別人一樣 |

- **誰能代送**：只有**現在的房主**，而且只能替**坐著電腦車的座位**；替真人、空座位、或不是房主的人送的，二進位一律安靜丟掉（和沒座位的人送 frame 一樣），JSON 回 `forbidden`。第一個 byte 254 不會和其他東西撞：瀏覽器送的 frame 是 kind 1／2，對時是 255；房間轉出去的第一個 byte 是座位（0–63）或 255。
- **裁定不變**：代送的 frame 拆掉前兩個 byte 後交給 `realtime.frame`，用電腦車的座位做 §4 的合理性檢查、判圈、§10 的拿取與使用、§10.1 的命中、20 秒沒聲音退賽，和真人一樣。電腦車的車款由 frame 的車 byte 決定（房主加的時候隨機抽，存在成員的 `look`）。
- **房主斷線＝電腦車退賽**：房主的 socket 一關、房主交給別人、或房主離線太久被換掉，比賽中的房間立刻對還沒跑完的電腦車套 `retire`（`RealtimeModule.abandon`）。起跑前也算（`retire` 現在在 loading、countdown 也收），所以不會卡住開賽。重新整理也是斷線；回來之後那一場的電腦車就不跑了，下一場（rematch）照常。
- **時間**：電腦車用房間的錶（和車手一樣的對時 ping）數到 GO，tick 從 GO 起算，伺服器照 §3 檢查。房主分頁在背景時計時器會變慢，電腦車最多一次追 2 秒的步數（frame 會一次送一串，別人畫的時候照 tick 插值）。
- **流量**：每台電腦車讓房主多上傳 20 個 frame／秒（34 bytes，約 0.7 kB/s），也讓房主多收自己代送的那些（33 bytes）。8 人房 1 人＋7 台電腦車：房主上傳約 5.4 kB/s、DO 收的和 8 個真人一樣（160 個／秒）。
- **測試**：`tests/worker/room-bots.test.ts`（權限、加入移除、房主斷線）、`tests/kart/roomBots.test.ts`（電腦車透過真的 `RoomHost` 跑完一圈並由房間判完賽）、`e2e/kart-race.spec.ts`（兩人＋1 台電腦車跑 1 圈）。

## 15. patch 只送陣列的差異、被打從頭轉、觀戰與重播的音效（2026-11-17，`feat/kart-net-deltas`）

補 §8.1 第 2 點與 #86 的兩個限制。程式在 [`ARCHITECTURE.md`](ARCHITECTURE.md) §4.22。

### patch（協定 v2）

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 房間 → 大家 | JSON `patch` 的 `ops` | 原本的 `set`／`del`，`set` 的路徑可以走進陣列（字串索引，例 `["game","racers","2","item"]`）；新的 `{ op: 'splice', path, at, del, items }`（陣列從 `at` 拿掉 `del` 個、放進 `items`） |

- **怎麼選**：同長度逐個位置比、一段 splice（共同開頭與結尾之間）、滑動窗（最舊的掉、最新的加，兩個 splice）、整個替換，取 JSON 最短的。道具賽常見的變化：拿箱＝`boxes` 一格＋那個人的 `item`＋`draws`；用道具＝`events` 掉一筆加一筆（滿 16 筆後）＋`shots` 尾巴加一顆＋`item` 變 null＋`used`；命中＝`shots` 拿掉一顆＋`events` 一筆。
- **相容性**：`PROTOCOL_VERSION` 1 → 2。舊頁面不懂陣列索引（會把陣列改成物件），所以部署後舊分頁重連時在 upgrade 就被 `versionMismatch`（4400）擋下，畫面說「網站已更新，請重新載入」（原本的流程，所有遊戲都一樣）。回合制遊戲的重播 API 沒有版本檢查，所以照 v1 送整個陣列（`diff` 的 `wholeArrays`）。卡丁車的二進位 frame、對時、道具 frame 都沒變。

### 被打中：從收到時從頭轉，自己的車本機預測

- **別人看**：`hit` 事件的 `at` 是房間收到被打那台車的 frame 的時間，patch 再過約半個來回才到。即時的效果改從收到時起算：自己的車馬上、從頭轉；別人的車晚 `DRAWN_BEHIND_MS`（100 ms，= §5 的插值緩衝）才轉、才噴星光、才響，那時畫出來的車剛好開到被打的地方。重播照事件的時間（樣本本來就照 tick 對齊）。
- **自己被打**：每一步（60 Hz）拿自己「上一步 → 這一步」的路線和 view 的 `shots` 比（`foreseeHit`，同 §10.1 的 `shotHits`），預測到就馬上暈、轉、響、HUD。冰雹與泥水坑要比邊緣近 `FORESEE_SLACK`（0.5／0.3 m）才預測：房間用 20 Hz 的 frame 與**到達時間**判，冰雹相對速度約 84 m/s，半個來回（30–60 ms）在冰雹的前進方向上差 2.5–5 m，但橫向的距離幾乎不變，所以擦邊的才會不同。雷雲時間到一定打到追的那台，不用留餘裕。泡泡罩開著不預測（房間會擋）。房間的 `hit` 晚 0–1.5 秒、同一種道具到就算確認，不再轉一次。
- **伺服器仍是唯一裁定**：預測不送任何東西，房間照 §10.1 判；房間判中而本機沒預測到的，照收到時從頭轉、暈整段。房間沒判中但本機預測了（擦邊、或剛好被別的車擋掉位置）：暈已經發生，收不回來，只是房間的狀態裡沒有那次命中。除錯：`window.__kartRace.foreseen`、`confirmed`。

### 觀戰與重播的音效

- **觀戰**：跟著被跟的那台車聽：它自己用道具、被打、泡泡破、打中別人全音量；別人的照距離（20 m 內全音量、150 m 外沒有，中間平方衰減）。延後 100 ms 響，和畫出來的打轉同時。不用新的線上格式（`events` 本來就在 view 裡）。
- **重播**：只有正常往前播經過事件那一刻才響；拖時間軸、±5 秒、暫停、倒退都不響；0.5×–2× 都播，4× 只播和被跟的車有關的；每幀最多 3 個（大聲的先），免得快轉時一次炸一堆。
- 只有道具音效（沒有引擎聲），照網站的靜音開關；瀏覽器要手勢才能出聲（頁面點過就可以，否則下一次按鍵或點擊）。

## 16. 高低差與跳台：frame 的「在空中」旗標（2026-11-17，`feat/kart-jumps`）

物理與賽道在 [`ARCHITECTURE.md`](ARCHITECTURE.md) §4.26。線上只多一個 bit。

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 瀏覽器 → 房間 → 其他人 | 同 §2 的 32／33 bytes | 旗標 byte（offset 1）的第 7 bit `FLAG_AIRBORNE`（128）：這台車正在空中（跳台起跳到落地）。只有在空中才設；平面賽道永遠是 0 |

- **為什麼不升版**：這個 bit 原本沒用。舊頁面的 `decodeFrame` 只看 0–4 bit 的旗標與 5–6 bit 的甩尾方向，第 7 bit 被忽略（那台車就畫在路面上，只是看起來沒跳）；frame 長度、其他欄位、轉送、重播、伺服器都不變。`PROTOCOL_VERSION` 維持 2。`decodeFrame` 只在 bit 有設時多一個 `airborne: true`，所以平面賽道的 frame 解出來和以前的物件一模一樣。
- **高度不上線**：別人的畫面用賽道的地形自己算：旗標是 0 就貼地（`groundAt`）；是 1 就用 `heightGuess`（從後面最近的起跳線、用插值後的速度算同一條拋物線，和那台車自己算的差不到 1 m）。所以不用多送 4 bytes 的高度，8 人房的流量不變。
- **伺服器裁定不變**（§4）：速度上限與「跳太遠」看的是水平速度與 x、z；空中水平速度不加速、不減速，所以不會超過門檻，不用另外放寬。檢查點照樣用 x、z 的線段；跳台橫跨整個路寬、路緣牆照常擋，所以空中的車也不會越過牆抄捷徑。
- **觀戰**照 frame 的旗標畫；**重播**的樣本沒地方放這個 bit（第 7 bit 已經是「絕對樣本」），一律用 `heightGuess`；幽靈車也一樣（速度從前後兩個樣本算）。
- **電腦車**（本機的對戰電腦與多人房的房主代跑）與 `npm run kart:loadtest` 的機器人送 frame 時也照實設這個 bit。
- **實測**（2026-11-17，PR #94 預覽站，`npm run kart:loadtest -- --track guanyin --bots 6`，3 圈道具賽、機器人照常飛過兩個跳台）：裁定 11,715 個 frame、丟 0、轉送後遺失 0；六台完賽、圈數和房間一致（最大差 17 ms）；每人上行 0.77、下行 3.63 kB/s；轉送 p50／p95／p99 38.7／52.3／72.2 ms；對時來回 38／51 ms。和 §15 的老街數字同一級（frame 數因為賽道短、比賽 96 秒而少）。

## 17. 團隊賽：分隊、團隊加速條、團隊噴射（2026-11-18，`feat/kart-team-race`）

規則與程式在 [`ARCHITECTURE.md`](ARCHITECTURE.md) §4.30。`PROTOCOL_VERSION` 維持 2：全部是新增（新訊息、選用欄位、道具 frame 的新 op），舊頁面不會送、收到多的欄位也不看。

| 方向 | 格式 | 內容 |
| --- | --- | --- |
| 瀏覽器 → 房間 | JSON `{ t: 'set_team', team: 0 \| 1 \| null, member? }` | 等待中或結束後（`playing` 回 `wrong_status`）。沒有 `member`＝自己；有＝房主幫那個成員（含電腦車）選，其他人回 `forbidden`，找不到人回 `bad_member`。`null` 交給房間自動分 |
| 房間 → 大家 | `RoomMember.team`（0 紅、1 藍，沒選就沒有這個欄位） | 等待室畫分隊；開賽時每個座位的 `team` 進 `init`（`Seat.team`），沒選的由 `assignTeams` 補到人少的那一隊 |
| 房間 → 大家 | JSON patch：`game.teams = { gauge: [紅, 藍], fills: [紅, 藍] }`、每台車的 `team`／`teamBoosts`／`teamUsed`／`teamUntil` | 只有團隊賽才有。`gauge` 以 4 點為一格（0–96），`fills` 是滿過幾次 |
| 瀏覽器 → 房間 | 二進位 8 bytes：kind 2、**op 3（`OP_TEAM`）**、0、0、int32 tick（同 §10 的道具 frame） | 「我剛噴了一個團隊噴射」。兩種模式都收（團隊賽不一定有道具）。**不轉送**；房主替電腦車送時照 §14 包 `PROXY_FRAME` |

- **累積（房間裁定）**：瀏覽器**不回報**集了多少。房間在 `realtime.frame` 收下一個 frame（§4 的合理性檢查都過了）之後，用 frame 自己的甩尾旗標、噴射旗標與速度算（`shared/kart/team.ts` 的 `teamGain`）：甩尾中每秒 14 點 × 速度／68 m/s（上限 1.25 倍，低於 12 m/s 不算）× 距上一個 frame 的時間（上限 100 ms，掉線回來不會補一大段）；噴射旗標在最近一次甩尾後 1.5 秒內由 0 變 1 算一次瞬間加速，5 點；再除以隊伍人數。自己的團隊噴射燃燒中（`teamUntil` 還沒到）不算。要灌水只能送假的甩尾旗標，而且一個 frame 最多算 100 ms：朋友圈夠用（§1：擋 bug，不是反作弊）。
- **不每個 frame 寫 state**：小數留在 DO 記憶體，跨過一格才送 `tgauge { team, gauge }`（一條加速條從 0 到滿最多 24 個 patch，每個約 60 bytes），滿了送 `tfill { team }`。DO 休眠醒來從 state 的那一格接著算（最多少算 4 點）。
- **發放**：`tfill` 讓那一隊**還在跑**的每台車 `teamBoosts` +1（上限 2，滿的就沒有），加速條歸零、`fills` +1。完賽與退賽的車不發。
- **使用**：瀏覽器看到自己的 `teamBoosts` 就能在本機馬上噴（物理裡先於個人存量、要等其他噴射噴完），同時送 `OP_TEAM`。房間只檢查「比賽中、這台車還在跑、手上有」，通過就 `tfire { seat, at }`：`teamBoosts` −1、`teamUsed` +1、`teamUntil = at + 4350 ms`。「噴完才能再噴」由車自己的物理把關，房間不再擋一次：兩邊的錶不會完全一樣，逆風或被打中也會讓它提早結束。
- **對帳**：本機可噴的數量＝`teamBoosts` −（本機噴過的次數 − `teamUsed`），所以 patch 還在路上時不會多噴一次；本機噴了但 5 秒內房間沒記到（frame 沒送到）就當沒發生，數量回到房間說的。中途重新整理的頁面從 `teamUsed` 起算。
- **別人看到藍色**：frame 格式沒動（旗標 byte 已經滿了）。別人的車在 `teamUntil` 還沒到而且 frame 的噴射旗標是 1 時畫藍色尾焰，否則照舊。延遲約一個來回（先看到一般顏色的火，再變藍）。
- **結果**：`GameResult.summary` 是 `games.kart.result.redWon`／`blueWon`（帶兩隊總分）或 `teamDraw`（沒人完賽）；`standings` 仍照個人名次，`score` 是那台車的得分，`note` 帶隊伍。
- **流量**：團隊賽比個人賽多的只有 JSON patch：每條加速條滿一次約 24 個 `tgauge`＋1 個 `tfill`（改每個隊員一格）＋每人一個 `tfire`，每個幾十 bytes；滿一次要幾十秒，所以每人下行只多幾十 B/s（實測見下）。上行每噴一次多 8 bytes。
- **壓測**：`npm run kart:loadtest -- --teams`（房間開成團隊賽；機器人在高速的彎道按住甩尾好讓加速條會動，拿到團隊噴射就噴）。報告多一行：兩隊各滿幾次、噴了幾個、還留幾個、兩隊總分與贏家。
